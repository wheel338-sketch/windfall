# MCP server for Windfall 1.0.1: draft hand-off (2026-10-14)

Branch `opus/mcp`, worktree `.claude/worktrees/mcp`, based on `main` at
`53b1c8fc` (v1.0.0).

**Nothing in this branch has been compiled, type-checked, linted or run.**
The machine's only build slot belonged to another agent, so no `cargo`,
`pnpm`, `vitest` or `tsc` ran. What was checked without building:

- `rustfmt --edition 2024` parses and formats every new or changed Rust file
  (so there are no syntax errors), and the new files are rustfmt-clean.
- A Python port of `message_guard.rs` (kept outside the repo) reproduces the
  current recorded list exactly (73 of 73 before this branch) and, after it,
  reports no unrecorded `format!` sentences, no recorded sentences gone, and
  no fixed error sentence missing from the catalog.
- A key check: the new catalog area has no key another area already has, and
  every `t(...)`/`message(...)` key the new TSX uses exists.
- The key-estimation, octave-band and tempo fixtures were simulated in
  Python/NumPy with the same maths (A minor, about 100 % of a 997 Hz sine's
  energy in the 1 kHz band, 120 bpm first candidate).
- Every file was re-read after writing; several real bugs were found and
  fixed that way (see "Least certain spots" for what reading cannot settle).

## What was built

The design followed the brief: a thin adapter over checked `Command`s, one
`CommandProposal` per edit, approved by the user, applied through
`Session::proposal_apply` as one undo step labelled with the agent's name.

### Decision: no `rmcp`

The protocol layer is hand-written in a new workspace crate instead of using
the `rmcp` SDK, and **no new external dependency was added**. Reasons:

1. The current MCP revision is `2026-07-28` (stateless: per-request `_meta`,
   `server/discover`, mirrored `Mcp-Method`/`Mcp-Name` headers,
   `resultType`), while clients still widely speak the `initialize`-based
   revisions. I could not verify which revisions the current `rmcp` release
   serves, nor its macro API, without compiling.
2. `rmcp`'s Streamable HTTP server is a Tower service that needs tokio,
   hyper and axum; Windfall serves its phone remote from a `std::net`
   thread, and this server follows that pattern.
3. The protocol layer is small (JSON-RPC dispatch plus a dozen methods) and
   isolated in `crates/windfall-mcp/src/{protocol,http,bridge}.rs`, with no
   I/O of its own, so it can be swapped for an SDK later.

The `rmcp` licence was not established (its README did not state it), and it
is not used. There are therefore **no SDK calls to verify**; the protocol
points to verify against real clients are listed under "Least certain
spots".

### Protocol served

- **Modern `2026-07-28`**: every request carries
  `params._meta["io.modelcontextprotocol/protocolVersion"]` and
  `clientCapabilities`; an unsupported version is `400` with `-32022` and
  `data.supported`; missing capabilities `400 -32602`; unknown method `404
  -32601`; results get `resultType: "complete"` and
  `_meta["io.modelcontextprotocol/serverInfo"]`; HTTP headers
  `MCP-Protocol-Version`, `Mcp-Method` and (for `tools/call`,
  `resources/read`) `Mcp-Name` must mirror the body (`=?base64?…?=` decoded),
  else `400 -32020`. `server/discover` is implemented.
- **Legacy `2025-11-25`, `2025-06-18`, `2025-03-26`**: `initialize`
  negotiates the version (an unknown request gets `2025-11-25`) and mints an
  `Mcp-Session-Id` (64 kept); requests carry it and `MCP-Protocol-Version`
  (absent means `2025-03-26`); an unknown session is `404`; `DELETE` ends a
  session. `structuredContent` and `resource_link` items are left out for
  `2025-03-26`.
- Methods: `initialize`, `server/discover`, `ping`, `tools/list`,
  `tools/call`, `resources/list`, `resources/templates/list`,
  `resources/read` (`windfall://project/summary`), notifications
  `notifications/initialized` and `notifications/cancelled` (cancels the
  running request of the same agent and id). JSON responses only, no SSE;
  `GET` is `405`; batches are refused.
- Tool failures are results with `isError: true` and a sentence saying what
  was wrong; unknown tools are JSON-RPC `-32602`.

### Transport and safety

- Off by default. Settings > AI agents (MCP) turns it on; it binds
  `127.0.0.1:<port>` (default 47133) only, accepts loopback peers only, and
  is restored at start-up only when left on.
- Per-install 64-hex bearer token in `<config>/mcp.json` (written through a
  private temp file, like `assistant-connection.json`); shown masked with
  Show / Copy / New token on the settings page.
- Every request: `Host` must be `127.0.0.1:<port>` or `localhost:<port>`
  (403 otherwise, against DNS rebinding), `Origin` absent or that host
  (403), path `/mcp` (404), `Authorization: Bearer <token>` compared in
  constant time (401 with `WWW-Authenticate`), `Content-Type:
  application/json` (415), `Accept` must allow JSON (406).
- Bounded: headers 16 KiB (431), body 1 MiB (413), chunked refused (501),
  POST without length (411), 10 s to send a request (408); 8 workers (503
  beyond), 50 connections a second (429); 16 proposals waiting, 16 running
  requests per agent; renders at most 120 s.
- Stdio bridge: `windfall-desktop --mcp-stdio [--config-dir <dir>]` runs
  before Tauri (first thing in `main`), finds the config folder like
  Tauri's `app_config_dir` (`%APPDATA%`, `~/Library/Application Support`,
  `$XDG_CONFIG_HOME`/`~/.config`, plus `org.windfall.Windfall`; or
  `WINDFALL_CONFIG_DIR`), reads port and token from `mcp.json` each time,
  exits 1 with a clear stderr line when the server is off or Windfall is not
  running, relays newline-delimited JSON-RPC, runs requests side by side (8)
  so a cancel can overtake a render, keeps the legacy session and reopens it
  with the client's own `initialize` when the app forgot it.
- No filesystem tools. Renders go only to
  `<recordings>/Agent renders/Render-*.wav`, newest 20 kept.

### Tools (31)

Read: `get_project_summary`, `list_notes`, `list_clips`, `get_mixer_track`,
`get_parameters`, `get_selection`, `list_instruments_and_effects`.

Edit (each files a proposal; returns `proposalId`, status, the undo label,
change lines for the agent, the ids it will create by kind, before/after
counts, and the stamp): `create_pattern`, `add_notes`, `remove_notes`,
`update_notes`, `set_steps`, `add_channel`, `add_effect`, `remove_effect`,
`move_effect`, `set_parameter`, `route_channel`, `route_track`, `set_send`,
`place_clips`, `move_clips`, `remove_clips`, `set_tempo_meter`,
`rename_and_color`, `write_automation`, `apply_raw_commands`. Each takes an
optional `title` (the undo step's name, prefixed with the agent's name) and
`explanation`.

Proposals: `get_proposal` (with `waitSeconds` up to 60), `apply_proposal`
(only when the user allowed the agent), `withdraw_proposal`.

Listen: `render_and_measure` (song, song range, or pattern × loops;
optional solo of one mixer track; integrated LUFS, LRA, short-term and
momentary max, true and sample peak, clipped samples, RMS, stereo
correlation, ≤48-window level over time, 10 octave bands, tempo via
`windfall_stretch::estimate_tempo`, key via a chroma over a radix-2 FFT and
Krumhansl–Kessler profiles, WAV path and a `resource_link`).

Positions are `bar:beat:tick` through `MeterMap` (pattern meter for notes,
song meter and its changes for clips/automation) or ticks; lengths are note
values (`1/4`, `1/8.`, `1/8t`), `bars:beats:ticks` durations or ticks;
pitches are scientific note names or MIDI numbers.

Every edit is previewed on a copy of the document with
`CommandProposal::validate` (the same stale/recording/registry/check rules
the apply uses) and then dispatched on that copy to work out what it creates
and changes; the ids each tool expects to create (from `next_id`) are
checked against what the copy made.

### Proposal registry (windfall-project)

`CommandProposal::batch` now also admits `AddMixerTrack`, `AddEffect`,
`RemoveEffect`, `MoveEffect`, `AddPlaylistTrack`, `UpdatePlaylistTrack`,
`AddClips`, `UpdateClips`, `RemoveClips`, `AddAutomation`,
`SetAutomationPoints`, and `UpdateSettings` of tempo **and** meter (still not
name, notes, timebase, swing or pan law). Files, samples, project
replacement, plugin state and nested batches stay refused. The BYOK
assistant's own schema (`assistant_protocol::command_schema`) is unchanged
and still narrower.

### Approval

`crates/windfall-mcp/src/approvals.rs`: pending → applying → applied /
failed, or rejected / withdrawn; stale is computed against the current
stamp; per-agent "apply without asking" until quit or server off; agent
named by its client's `clientInfo` (title, else name), kept per legacy
session. The panel (`features/mcp/panel.tsx`, main window only) is
non-modal: label, agent, explanation, localized counts, "Show the commands"
(exact JSON), Apply / Reject / Dismiss, trust checkboxes, render indicator
with Stop. It follows the `mcp:panel` event. It also reports the selected
channel, mixer track and centre view (`mcp_focus`), which the session keeps
only while the server listens.

## Least certain spots

1. **`static TOOLS` holds closures** (`schema: || …`) coerced to `fn()`
   pointers in a static initializer. I believe non-capturing closures
   coerce in constant contexts; if not, turn each into a named `fn`.
2. **`json!` recursion depth.** The summary and some test literals are
   large; if the compiler hits the macro recursion limit, add
   `#![recursion_limit = "256"]` to `windfall-mcp/src/lib.rs` (and the
   desktop crate for its tests).
3. **Real clients against the dual-era endpoint.** Verify with Claude Code
   and Claude Desktop (stdio) and an HTTP client: which revision each
   sends, that legacy session ids are echoed, that modern clients send the
   mirrored headers, and that `notifications/cancelled` arrives. A client
   that gets `401` may try OAuth discovery under `/.well-known/…`, which
   answers `404`.
4. **`--mcp-stdio` from the release build.** `main.rs` runs it before
   Tauri, but release builds use `windows_subsystem = "windows"`. I expect
   inherited pipes to work for stdin/stdout/stderr (the plugin scanner
   writes to stdout the same way), but it needs a check with Claude Desktop
   on Windows, including that the client sees the bridge's stderr.
5. **The executable's installed path/name** in docs/MCP.md is an example
   (`%LOCALAPPDATA%\Windfall\windfall-desktop.exe`); the settings page shows
   `current_exe()`, which is authoritative. Check the NSIS install and the
   macOS bundle path.
6. **Solo in renders** sets `solo` on that mixer track of a project copy.
   This assumes Windfall's solo silences every other track while keeping the
   soloed track's path to the master (the render test expects the hat's
   track alone to be silent).
7. **Id prediction.** Edit tools predict created ids from `next_id` in each
   command's documented order; the preview refuses ("other ids than the
   tool expected") if a command allocates differently (for example
   `AddChannel` with an instrument that allocates something extra). The
   tests would show it.
8. **Session test timing and ports**: `the_server_is_off_by_default_and_
   restores_when_left_on` relies on `Listener::drop` joining the accept
   thread so the port is free after `Rig::restart`; the TCP tests use
   ports picked by binding port 0 first.
9. **Heuristics on real music**: key from notes needs 8 pitched notes and
   skips samplers and drum instruments; the audio key and tempo are
   estimates (tempo can be the half or double; the alternatives are
   returned).
10. **Hand-written TS bindings** imitate ts-rs output (doc comments
    included); the generated files may differ in layout.
11. **Approval panel placement** (`fixed bottom-10 left-3`) was not seen
    on screen; it may need moving off the status bar or the mixer.
