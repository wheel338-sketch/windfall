### `win-playlist-arrangements` — software complete; Rust executed, UI unverified

Implemented:

- `Command::AddArrangementLayout { name, copy }`
  (`crates/windfall-project/src/lower/playlist_layouts.rs`). A project with
  no arrangement first keeps its present timeline as "Arrangement 1". The
  new layout takes the active layout's lanes. With `copy` every clip of the
  active layout is cloned as a new clip entity, and clip groups among the
  copies are cloned too; without it the layout starts empty. The new layout
  becomes active. One undo step.
- `Command::RemoveArrangement` now also removes the clips that only the
  removed layout listed. Clips another layout lists, and clips no layout
  ever listed, stay.
- The engine already played only the active layout; nothing changed there.
- UI: the arrangements popover has **New empty layout** and **Duplicate
  layout**. An arrangement with no clips now shows its lanes (it showed
  nothing before, so nothing could be placed on a new layout).

Independent positions follow from clip identity: a copied layout owns its
own clips, so a move, resize, mute or delete in one layout cannot reach
another. `SetArrangementReferences` can still list one clip in two layouts
on purpose; the two buttons never do.

Tests:

- Executed: `crates/windfall-project/tests/playlist_layouts.rs` —
  `first_layout_keeps_the_present_timeline_and_an_empty_layout_starts_clean`,
  `a_copied_layout_owns_independent_clip_positions`,
  `removing_a_layout_removes_only_the_clips_it_alone_placed`,
  `files_written_before_layouts_and_linked_tracks_still_load`. Every edit
  in them is checked for one history entry, exact undo, exact redo and a
  save and reload.
- Executed: `crates/windfall-engine/tests/engine/playlist_layouts.rs` —
  `a_copied_layout_plays_its_own_clip_positions_live_and_offline` (offline
  render and callback output bit-equal, per layout).

### `fmt-export-playlist-tracks` — software complete; engine executed, session and UI unverified

Semantics, stated in `crates/windfall-engine/src/stems/playlist.rs`: a
playlist stem is the song with only that lane's pattern and audio clips
placed, heard at the output through its mixer tracks, buses and the
master. Automation plays in every stem. Bus and master processing is
included; a level-dependent processor or a sidechain detector reacts to
each lane alone, so stems add up to the mix only where the path is linear.
A lane the mix does not play has nothing to give. Every stream is as long
as the mix.

Implemented: `render_playlist_stems` and `playlist_stems` in the engine;
`Session::export_playlist_tracks`, Tauri command `export_playlist_tracks`,
IPC `ExportPlaylistStems`, `ExportedFile.playlistTrack`; a section in the
export dialog.

Tests:

- Executed: `crates/windfall-engine/tests/engine/playlist_stems.rs`, 8
  cases, among them lanes that share a pattern, a channel and a mixer
  track, a limiter on the master, an automatic tail, cancellation and
  the active arrangement.
- Not executed: `session/tests/playlist_export.rs` (4 cases: files on
  disk decoded and summed, chosen lanes, refusals, cancellation) and
  `features/export/playlist-tracks.qa.test.tsx` (4 cases).

Remaining gates: run the session and UI tests. **No sidechain test was
written**: the sidechain statement above is documented and follows from
the implementation, but nothing measures it. A region export with
playlist stems is allowed and untested.

### `win-playlist-instrument-audio-tracks` — software complete; Rust executed, UI unverified

Implemented:

- `TrackKind::AudioTrack { mixer }` beside the existing kinds.
- `AddInstrumentTrack` creates a channel, its mixer track and a lane
  linked to the channel. `AddAudioTrack` creates a mixer track and a lane
  linked to it. One undo step each.
- Engine: a pattern clip on an instrument track plays only the linked
  channel (`PlanClip.only`, one comparison in the sequencer's song loop).
