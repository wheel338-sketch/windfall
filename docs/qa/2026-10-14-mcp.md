### Fixed in the product

- **Modern-era cache hints.** Under revision `2026-07-28` the results of
  `tools/list`, `resources/list`, `resources/templates/list`,
  `resources/read` and `server/discover` must carry `ttlMs` and
  `cacheScope`. The Inspector (`@modelcontextprotocol/client` 2.3.1) refused
  `tools/list` without them: "Invalid result for tools/list … ttlMs … expected
  number". They are now added, `cacheScope: "private"`. `ttlMs` is
  `LIST_TTL_MS` = 300,000 ms for the lists, which are fixed while the app
  runs, and 0 for the summary read and for discovery. Legacy results are
  unchanged. New test: `modern_cacheable_results_say_how_long_to_keep_them`.
- **`render_and_measure`'s `region` had no type** in its schema. The
  Inspector, like other clients that coerce arguments by schema type, sends
  an untyped property as text, and the tool refused `{"patternId":…}`. It is
  now `"type": "object"` with `from`, `to`, `patternId`, `loops`. Leaving it
  out still means the song, and the code still accepts `"song"`.
- **A user's own edit did not refresh the approval panel.** A waiting
  proposal went stale (the apply was refused), but the window still showed
  it as applicable with Apply enabled until something else sent the panel.
  The session publishes document changes with its state locked, and the
  panel reads that state. So when a patch or a loaded project is published
  while a proposal waits, the panel is now sent from a short-lived thread
  once the lock is free (`Session::mcp_project_changed`); a burst of edits
  sends it once. The session test
  `proposals_are_refused_while_recording_and_once_stale` now also requires
  the window to receive a panel with the proposal stale.

  CLI mode, with `@modelcontextprotocol/client` 2.3.1 inside. Installed with
  npm into `%LOCALAPPDATA%\Temp\wf-mcp-inspector`, outside the repository,
  and run from there.
- **Node:** it ran on Node v24.22.0 LTS, the official zip (SHA-256
  `f9683a19…f80c3`, checked against `SHASUMS256.txt`), unpacked into
  `%LOCALAPPDATA%\Temp\wf-mcp-node`. On this machine's Node 26.4.0 the CLI

  The abort is `Assertion failed: !(handle->flags & UV_HANDLE_CLOSING),

  fault in the client process, not the server's; the smoke's
  `MCP_SMOKE_INSPECTOR_NODE` picks the Node it runs on.

  made an empty `%USERPROFILE%\.mcp-inspector\storage` at the first run,
  which was removed.
- **Agent name:** the CLI names itself `inspector-cli`, so undo steps read
  `inspector-cli: New pattern for the bass`.

## 6. Unresolved

- **Claude Desktop and Claude Code were not run** against the server. Their
  configuration in `docs/MCP.md` follows their documented formats. The
  protocol was verified with the official SDK's client (the Inspector), in
  both eras.
- **`notifications/cancelled`** from a real client was not observed. The
  Inspector CLI makes one call per process and never cancels. The unit test
  covers it.
- **Schema portability warnings:** `--strict` reports 28 warnings across 11
  tools, 0 errors. Positions, lengths and pitches are typed
  `["string","integer"]`. That is legal JSON Schema, but a client that maps
  schemas onto a single-`type` dialect (Gemini function declarations) may
  drop the constraint. Splitting them into `anyOf` would silence it. Left
  as is.
- **Musical estimates:** the render's key estimate is not meaningful on
  pitched drum samples (it said G♯ minor for a C minor seventh played on a
  kick). The tempo matched to 0.1 BPM here, but can come out at half or
  double; the alternatives are returned.
- **The approval panel** covers the lower browser and the first mixer strip
  while it is shown (3.4).
- **Node 26.4.0 on Windows** aborts the Inspector CLI as it exits (3.1).
  Users running MCP tools on that Node may see the same; it is not
  Windfall's.
- **Platforms:** the stdio bridge's macOS path and Linux config folder were
  not run; 1.0.1 ships for Windows only.
- Everything in the updater record's "Unresolved" still stands: 1.0.0 users
  install by hand once, the key needs a backup, no Authenticode.
